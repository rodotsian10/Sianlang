# SianLang 구현 검토

> 이 문서는 수정 전 상태의 기록입니다. 아래 재현 문제는 0.2.0에서 수정하거나 지원 규칙과 명시적 오류로 정리했으며, 0.3에서는 함수/출력/예외 문법을 추가 확장했습니다. 현재 내용은 [수정 내역](../CHANGELOG.md), [문법 규칙서](../설명서/시안랭-문법규칙서.md), [회귀 테스트](../tests/test_runtime.py)를 참고하세요. 당시 실행 결과는 비교를 위해 보존했습니다.

검토일: 2026-09-15. 대상: `main.c` 254줄, 문서 전체, VS Code 확장 소스, 기존 실행 파일과 예제.

## 검증 범위

- 원본 소스와 기존 실행 파일은 수정하지 않았다. 이 폴더에 검증용 파일만 추가했다.
- GCC 16.1.0으로 `-std=c11 -Wall -Wextra -Wpedantic -Wconversion -g` 빌드 성공, 경고 없음. 경고가 없어도 아래 실행 오류가 발생한다.
- `check.py`로 53개 독립 프로그램을 실행했다. 결과는 `results.json`, 입력은 `cases/`에 있다. 정상 비교용 사례도 포함하므로 53이라는 수는 버그 개수가 아니다.
- `check_existing.py`로 기존 예제 4개를 실행 파일 3개에 대해 실행했다. 결과는 `existing-results.json`에 있다.
- 강제 종료 테스트는 별도 프로세스에서 수행하고 3초 제한을 적용했다. `error_loop`는 제한 시간에 종료시켰다.
- 메모리 누수는 소스의 할당/해제 경로 검토로 확인했다. 누수량 측정, sanitizer, VS Code Extension Host 통합 테스트는 수행하지 않았다. PowerShell 실행 명령 오류는 실제 셸에서 재현했다.
- 이 검토가 모든 가능한 입력의 무결함을 보증하지는 않는다. 아래에서 실행 확인과 정적 분석, 명세 결정이 필요한 사항을 구분한다.

## 1. 최우선: 비정상 종료와 메모리 안전성

### 1.1 `% 0`이 언어 오류 대신 프로세스를 죽인다 — 실행 확인

위치: `main.c:157`. 재현: `zero_modulo.sian`의 `log 1 % 0`.

종료 코드 3221225620(0xC0000094), 오류 메시지 없음. `/`만 0을 검사하고 `%`는 C 연산을 그대로 실행한다. `/`와 `%` 모두 연산 전 타입과 0을 검사해야 한다. 최소 정수 / -1 및 최소 정수 % -1의 범위 초과도 처리해야 한다.

### 1.2 숫자·식별자·매개변수 길이를 넘으면 메모리를 침범한다

위치: `main.c:126`, `129`, `181`.

- `token[256]`에 숫자와 식별자를 길이 검사 없이 쓴다. 300자리 숫자는 3221225477(0xC0000005)로 실제 종료했다.
- 300자 식별자도 경계를 넘겨 쓴다. 이번 실행은 변수 오류로 끝났지만 안전하다는 의미는 아니다.
- 매개변수 이름을 `params[][64]`에 `strcpy`한다. 100자 매개변수는 범위를 침범한다.
- 매개변수 개수를 `MAX_ARGS=16`과 비교하지 않는다. 17개부터 배열 밖을 쓴다. 이번 실행에서 호출 인수 오류가 발생했어도 그 전에 메모리가 이미 훼손된다.

길이/개수를 쓰기 전에 검사하고, 초과 시 위치가 있는 언어 오류로 종료해야 한다.

### 1.3 문자열을 반복 처리하면 메모리가 누적된다 — 정적 분석

위치: `main.c:32-33`, `135-148`, `155-171`, `253`.

- 문자열 인수 `args[]`를 정상 호출과 오류 반환 경로에서 해제하지 않는다. `input("질문")`의 질문 문자열도 포함된다.
- 함수 종료 시 지역 변수의 문자열을 해제하지 않는다.
- 문자열 비교, 부정, 잘못된 산술 등에서 임시 문자열을 해제하지 않는다.
- 프로그램 종료 시 전역 변수와 소스 문자열 정리도 없다. 이것은 OS가 회수하지만, 반복 호출 중 누수는 긴 게임 실행에 직접 영향을 준다.

각 `Value`의 소유자와 복사/이동/해제 규칙을 먼저 정해야 한다. 현재의 `malloc` 방식도 명확한 수명 관리가 있으면 사용할 수 있다.

### 1.4 정수 범위와 실수→정수 변환이 검사되지 않는다

위치: `main.c:28`, `81-103`, `126`, `155-160`.

이 Windows 빌드에서 `log 2147483648`은 2147483647, `log 2147483647 * 2`는 -2를 출력했다. `strtol` 범위 오류와 C의 부호 있는 정수 오버플로를 처리하지 않는다. `float_value()`는 모든 실수를 무조건 `long`으로도 변환한다. 무한대·NaN·범위 밖 실수의 변환은 C에서 안전하지 않다. `input`의 `strtod`도 이러한 값을 허용할 수 있다.

정수 폭, 오버플로 정책, 비유한 실수 허용 여부를 정하고 모든 생성/연산/변환 경로에 적용해야 한다.

`Value`에 정수·실수·불리언 표현을 동시에 저장하는 구조가 이 문제들을 키운다. 유효한 타입을 먼저 확인하고 그 타입의 값을 읽도록 연산을 구성해야 한다.

## 4. 문법 검증과 블록

### 4.1 표현식 뒤의 쓰레기 문자를 무시한다 — 실행 확인

위치: `main.c:173`. `evaluate()`가 전체 입력을 소비했는지 확인하지 않는다.

`log 1 nonsense`, `log 1 2`, `log 1)` 모두 오류 없이 1을 출력한다. `log 1.2.3`은 1.2를 출력한다. `1 == 1 == false`에서는 마지막 비교를 무시한다. 연쇄 비교를 지원하지 않기로 하더라도 남은 부분은 오류여야 한다.

### 4.2 들여쓰기 규칙이 검증되지 않는다 — 실행 확인

위치: `main.c:176`, `185-236`.

`if true` 뒤 본문이 없어도 오류가 없다. 같은 블록에 4칸과 2칸 들여쓰기가 섞여도 실행된다. 최상위에서 이유 없이 들여쓴 문장도 실행된다. 문법 규칙서 12장의 필수 본문 규칙과 다르다. 빈 `while true`는 빠져나올 본문도 없이 계속 반복할 수 있다.

블록 진입/종료를 토큰이나 파싱 단계에서 확정하고, 허용되지 않은 들여쓰기와 잘못된 dedent를 검증해야 한다.

### 4.3 잘못된 문장이 정상 문장으로 등록된다 — 실행 확인

위치: `main.c:180`, `214-229`.

`def test(x`처럼 닫는 괄호가 없어도 함수가 등록되고 호출된다. `else garbage`도 else로 실행된다. `sscanf`의 대입 개수는 문장 전체가 올바르다는 증거가 아니다.

### 4.4 실행하지 않는 블록은 문법 오류조차 검사하지 않는다

`if false` 아래에 임의의 잘못된 문장을 넣어도 성공한다(`unreachable_syntax`). 실행 중 파싱하는 현재 방식의 결과다. 문법 오류를 언제 보고할지 명세에 정할 필요가 있다. 파일을 먼저 파싱하면 실행 도중 뒤늦게 문법 오류가 드러나는 상황을 줄일 수 있다.

## 5. 함수와 변수 범위

### 5.1 매개변수 없는 함수를 등록하지 못한다 — 실행 확인

위치: `main.c:180`. `def greet()`의 매개변수 스캔이 실패해 등록되지 않는다. `log greet()`는 function not found. 문법 규칙서에 나오는 `greet()`, `done()` 예제가 해당된다.

### 5.2 매개변수와 지역 선언이 바깥 변수를 덮어쓴다 — 실행 확인

위치: `main.c:64-71`, `148`.

```sian
int x = 100
def identity(x)
    return x
log identity(7)
log x
```

실제 결과는 7, 7. 일반적인 지역 매개변수라면 7, 100이어야 한다. 함수 안 `int x = 7` 선언도 같은 문제다. `assign()`이 부모 환경까지 검색해서 기존 변수를 갱신하기 때문이다. 현재 환경에 새 변수를 만드는 선언과, 기존 변수를 변경하는 대입을 분리해야 한다. 재귀 호출도 매개변수 이름이 같아서 영향을 받는다.

### 5.3 함수가 호출자의 지역 변수까지 읽는다 — 실행 확인, 명세 결정 필요

위치: `main.c:148`. `local.parent = p->env` 때문에 함수가 정의된 위치보다 호출 위치에 따라 이름의 의미가 바뀐다. `dynamic_scope`에서 `read()`는 자신이 정의된 곳에 없는 `secret`을 호출자에게서 읽어 42를 반환한다. 이런 동작을 동적 범위라고 한다. 일반적인 어휘적 범위, 즉 함수가 정의된 위치를 기준으로 찾는 방식을 의도했다면 버그다.

### 5.4 함수 등록 규칙이 실행 순서/범위와 분리되어 있다

위치: `main.c:178-182`. 실행 전 모든 줄에서 함수를 수집한다. 따라서 `if false` 내부 함수도 호출할 수 있다(`conditional_definition`). 중첩 정의도 전역 목록에 들어가고 동일 이름은 마지막 등록 항목을 선택한다(`145`). 전방 참조 자체는 선택 가능한 기능이나 조건부/중첩/중복 정의 규칙은 정해야 한다. 지원하지 않으면 명시적으로 거부해야 한다.

### 5.5 함수 호출을 독립 문장으로 쓸 수 없다 — 확인된 기능 한계

`greet(7)`은 unknown statement이고 `log greet(7)` 같은 표현식 자리에서만 호출된다(`call_statement`). 현재 문서의 표현식 내부 호출 설명과는 일치하므로 명세 위반으로 세지 않는다. 그러나 화면 그리기·소리 재생·상태 변경 함수는 반환값 없이 호출하는 경우가 많아 게임 언어에서는 우선 추가해야 한다.

## 6. 오류와 반복 실행

### 6.1 함수 안 `iferror`가 프로그램을 종료하지 않는다 — 실행 확인

위치: `main.c:191-196`, `148`.

```sian
def fail(x)
    iferror("stop")
log fail(0)
log "after"
```

오류와 함께 0, after를 출력한 뒤 마지막에 종료 코드 1을 반환한다. 규칙서는 즉시 프로그램 종료라고 설명한다. `Flow.returned` 하나로 정상 반환과 오류를 표현해 호출자가 오류를 정상 반환처럼 처리한다. NORMAL / RETURN / ERROR 등 흐름 상태를 분리하고 평가 결과에도 오류를 전파해야 한다.

### 6.2 일반 오류 후에도 출력·대입·반복을 계속한다 — 실행 확인

위치: `main.c:34`, `173`, `185-244`.

- `log missing` 뒤에 0과 다음 로그까지 출력한다.
- `n = 1 / 0`은 기존 n을 오류 값으로 덮어쓴다.
- `while true` 안 `log missing`은 오류를 계속 출력하며 끝나지 않는다. 테스트 제한 3초로 중단했다.
- 호출 인수나 괄호 파싱에서 오류가 발생해도 이후 실행을 차단하는 공통 경로가 없다.

오류 복구를 의도하더라도 실패한 식을 정상 값처럼 사용해서는 안 된다. 현재 작은 인터프리터에는 첫 오류에서 중단하는 규칙이 구현과 사용자 이해 모두에 단순하다.

### 6.3 `while`/`loop` 최초 조건을 두 번 평가한다 — 실행 확인

위치: `main.c:206`, `233`.

조건을 첫 번 검사해놓고 결과를 사용하지 않은 채 반복 루프에서 다시 평가한다. `double_condition`에서 조건 함수가 카운터를 증가시키면 본문 실행 없이 카운터가 2가 된다. 조건에 입력이나 함수 호출이 있으면 명확하게 잘못된 동작이다.

### 6.4 오류 설명이 원인을 충분히 알려주지 않는다

위치: `main.c:34`, `146-152`, `239`.

변수 이름, 함수 이름, 실제/기대 자료형, 인수 개수, 파일 이름, 열 위치, 호출 경로가 없다. `int n = 1 + 2`에도 입력과 무관한 `input does not match variable type`가 나온다. 쉬운 언어의 중요한 부분은 짧은 문법과 함께 고칠 방법이 보이는 오류 메시지다.

## 7. 입력과 제한

- **입력 출처에 따라 문자열 변환이 달라짐** (`main.c:33`, `81-110`): `str s = input()` 후 `int n = s`는 성공한다. 같은 내용의 일반 문자열은 실패한다. 복사에 `from_input`이 유지되지만 문자열 덧셈을 거치면 사라진다. 문서보다 넓고 눈에 보이지 않는 변환 규칙이다(`input_origin`).
- **재입력에서 자동 변환 없음** (`240`): `int n = 1; n = input()`는 문자열을 저장한다. 이어서 `n + 1` 하면 숫자 1이 버려진다(`input_reassignment`). 선언과 재대입의 일관성을 정해야 한다.
- **EOF와 빈 입력이 구별되지 않음** (`141`): EOF에 일반 빈 문자열을 반환한다. 숫자 선언에서는 자료형 오류가 나고, 입력 반복에서는 끝을 알아채기 어렵다(`input_eof`).
- **긴 입력의 나머지가 다음 입력으로 넘어감** (`138-143`, 정적 분석): `fgets`로 1023바이트만 읽고 남은 줄을 소비하지 않는다. 긴 답변 하나가 다음 질문의 답까지 되어버릴 수 있다.
- **변수 256개 초과 시 메시지 없이 종료** (`69`, `variable_limit`).
- **함수 128개 초과 시 정의 무시** (`181`, `function_limit`). 나중에 호출할 때 존재하지 않는 함수 오류만 난다.
- **호출 인수 16개 초과 진단 부정확** (`136`, 정적 분석): 배열 쓰기는 제한하지만 추가 식을 소비하지 않아 닫는 괄호 오류로 이어진다. 한도 초과를 직접 알려야 한다.
- **재귀 깊이 제한 없음** (`148`, 정적 분석): 호출마다 256개 변수 공간을 가진 `Env`를 C 스택에 놓는다. 깊은 재귀는 언어 오류 대신 스택 고갈로 끝날 수 있다.

## 8. VS Code 확장과 배포

### 8.1 PowerShell 실행 버튼 명령이 잘못됐다 — 셸에서 재현

위치: `sianlang-vscode/extension.js:41`, `48-50`.

확장은 `"실행파일경로" "소스경로"`를 터미널에 전송한다. PowerShell에서 이 명령은 ParserError다. 실행 파일 앞에 호출 연산자 `&`가 필요한 형식이다. VS Code 호스트에서 버튼을 직접 누른 검증은 하지 않았지만, 실제로 만드는 명령 형태가 이 환경에서 실패함을 확인했다.

셸 종류별 안전한 인수 전달 또는 셸 인용을 직접 조립하지 않는 실행 방식을 사용해야 한다. 현재 큰따옴표 감싸기와 `\"` 치환만으로는 PowerShell의 `$`, 백틱 등의 해석도 막지 못한다(정적 분석). 단순히 `&`만 붙이면 모든 셸/경로 문제가 해결되는 것은 아니다.

### 8.2 실행 파일이 실제로 서로 다르다 — 실행 확인

루트 `Sianlang.exe`는 현재 예제의 `str`, `log`, `iferror` 등을 인식하지 못하면서 종료 코드 0을 반환한다. `SianlangA.exe`와 새로 빌드한 실행 파일은 기존 입력 예제와 최상위 iferror 테스트에서 같은 정상 결과를 냈다. 기본 문서는 `Sianlang.exe`, 확장은 `SianlangA.exe`를 가리킨다. 사용자는 같은 프로젝트에서 실행 경로에 따라 다른 언어를 보게 된다.

공식 실행 파일 이름과 빌드 명령을 통일하고 버전을 표시해야 한다. 이번 검토에서는 기존 바이너리를 덮어쓰지 않았다.

### 8.3 저장 실패 처리 없음 — 정적 분석

위치: `extension.js:21`. `document.save()`의 성공 여부를 확인하지 않고 실행하며 Promise 실패 처리도 없다. 저장에 실패하면 오래된 파일을 실행하거나 이유를 제대로 표시하지 못한다.

### 8.4 강조 표시·아이콘·설정의 불일치 — 파일 검토

- TextMate 문법에 `iferror`가 없다.
- 이스케이프 및 `.5` 같은 숫자 강조 규칙은 실행기가 지원하는 문법과 다르다.
- 아이콘 테마 JSON이 있지만 `package.json`의 `contributes.iconThemes`에 등록되지 않았다. README의 Activity Bar 아이콘 설명에 대응하는 `viewsContainers` 등록도 없다. 확장 목록용 `icon` 등록과 서로 다른 기능이다.
- 저장소 전체에서 빌드/회귀 검증을 자동 실행하는 구성이 보이지 않는다. 기존 `.sian` 파일은 예제이며 예상 출력/종료 코드를 자동 비교하는 테스트는 아니다.

## 9. 문서 정리

- `설명서/01-개요`는 `넣기`, `보여줘`, 변수 A/B/C가 현재 구현이라고 설명한다.
- `04-실행모델`은 줄 단위 즉시 실행과 옛 명령어를 설명하지만 실제 코드는 전체 소스를 읽고 함수를 사전 등록한다.
- `05-표현식`은 현재 지원 표시와 함께 계산식 미지원이라고 설명한다.
- `07-복합문`은 중괄호와 한글 문법을 설명하고 현재 들여쓰기 구현과 다르다.
- `06-단순문`, `08-최상위요소`에도 옛 명령어/현재 미지원 목록이 남아 있다.
- `09-전체문법`은 `return`, `iferror`, `else if` 등의 현재 동작을 충분히 반영하지 않는다.
- 기준 규칙서의 빈 함수 예제, 필수 본문, 즉시 오류 종료는 구현과 어긋난다.

기준 문법 하나를 정하고 모든 예제를 실제 실행 검증 대상으로 삼아야 한다. 계획 문법은 현재 지원 문법과 명확히 구분해야 한다.

## 10. 목표에 대한 설계 의견 — 버그와 구별

목표가 파이썬보다 쉽게 2D 게임을 만드는 것이라면, 지금 가장 필요한 것은 문법 종류 추가보다 예측 가능한 기본 동작이다.

1. **대표 문법을 줄이기.** 함수 정의 4개와 bool 별칭은 학습량과 문서/도구 관리 비용을 늘린다. 별칭을 남기더라도 공식 예제는 하나로 통일한다. `f`는 함수 정의 키워드이므로 함수 이름으로 쓰는 경우와도 충돌하기 쉽다.
2. **타입 규칙 선택.** `score = 0`으로 자동 선언할지, `int score = 0`을 유지할지 결정한다. 쉬움이 목표라면 타입 추론이나 선택적 타입 표기를 검토할 수 있다. 어떤 선택이든 선언/대입/인수에서 일관되어야 한다.
3. **연산 규칙 명시.** `/`, `%`, 서로 다른 타입의 비교와 덧셈, 조건의 참/거짓 변환, 반복 횟수, 숫자 범위를 작은 표 하나로 정의한다.
4. **오류 이름을 동작과 맞추기.** `iferror`는 오류를 검사/처리할 것처럼 읽히지만 실제 목표는 무조건 오류 발생이다. `error` 같은 직접적인 이름이 이해하기 쉽다.
5. **핵심 누락 기능을 단계적으로 추가.** 독립 함수 호출, `and`/`or`와 단락 평가, `break`/`continue`, 명시적 변환이 우선이다. 목록/객체는 여러 적·탄환·스프라이트 상태를 다루기 전에 필요하다. 이들은 미구현 기능이지 모두 현재 버그는 아니다.
6. **주석과 논리 연산 충돌을 피하기.** `||`를 주석으로 유지한다면 논리 OR 문법은 `or`처럼 별도로 정해야 한다.
7. **게임 API가 쉬움을 만들게 하기.** 사용자가 매번 창 생성, 이벤트 처리, 프레임 시간 계산을 작성하지 않도록 기본 런타임이 관리하고, 사용자는 초기화·갱신·그리기와 키 입력을 간단히 작성하는 구조를 목표로 삼는다.
8. **장시간 실행에 맞추기.** 현재는 반복할 때마다 같은 문자열을 다시 파싱하고 함수 호출마다 큰 환경을 생성한다. 성능 수치는 측정하지 않았으나 미리 파싱한 구조를 재사용하고 문자열 수명을 관리하는 것이 게임 루프에 적합하다.

권장 내부 단계:

```text
소스 → 토큰(이름·숫자·문자열·들여쓰기) → 문법 트리 → 실행
```

문법 트리는 계산식과 블록의 구조를 한 번 읽어 저장한 것이다. 바이트코드나 JIT까지 만들 필요는 없다. 작은 트리 실행기부터 시작하면 문법 검사와 실제 실행을 분리할 수 있다.

## 권장 작업 순서

1. 정수 연산 타입, `% 0`, 버퍼/매개변수 경계, 오류 전파, 함수 매개변수 덮어쓰기 수정.
2. 문자열/주석/숫자 토큰화와 입력 끝 검증. 들여쓰기 및 함수 문법을 실행 전 검사.
3. 선언/대입/함수 범위와 문자열 소유권 정리. 빈 함수와 독립 호출 지원.
4. 검토 사례에서 확정한 기대 출력·종료 코드를 자동 비교하도록 회귀 테스트 구성. 현재 `check.py`는 관찰 기록용이며 통과/실패를 자동 판정하지 않는다.
5. 실행 파일 이름, 확장 실행 명령, 문서 통일.
6. 창 하나를 열어 도형 하나를 키보드로 움직이는 첫 게임 예제. 이후 이미지·소리·목록/객체를 필요에 맞춰 확장.

## 재실행

```powershell
gcc -std=c11 -Wall -Wextra -Wpedantic -Wconversion -g main.c -o review/Sianlang-review.exe
python review/check.py
python review/check_existing.py
```

첫 스크립트는 Windows 전용 오류 대화상자 억제 처리를 포함한다. 비정상 종료·무한 반복 사례도 실행한다. 원본 파일 대신 `review/cases`만 생성/갱신한다.
